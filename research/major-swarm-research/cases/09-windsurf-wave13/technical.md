### Prompting Strategy

#### Real-Time Awareness System

**Context Gathering** (automatic, no prompting required):
> "Cascade tracks user actions across multiple dimensions: edits, commands, conversation history, clipboard, terminal commands to infer intent and adapt in real time"

**Integrated Inputs**:
- File tracking: edited and viewed files
- Terminal activity: shell commands
- Clipboard integration: content transfer
- Visual inspection: browser integration

**Result**: "Real-time awareness of user actions, reducing context-prompting requirements"

#### Planning Mode Prompting

**Two-Tier Prompting Architecture**:

1. **Long-Term Planning Prompt** (to planning agent):
   - Persistent `plan.md` file generation
   - Overall project context understanding
   - Strategy formulation
   - **Model Used**: "More powerful model handles long-term reasoning in the background"

2. **Short-Term Execution Prompt** (to user-selected model):
   - Task-specific code generation
   - File editing operations
   - Based on plan generated by planning agent
   - **Model Used**: User-selected model from picker

**Workflow**:
> "Cascade generates a persistent planning file called 'plan.md' and acts based on it. Technically, it consists of a combination of two elements: Cascade conversations for short-term actions and planning files for long-term reasoning"

**Benefit**: "Allowing AI to work on long-term tasks without losing context while enabling developers to intervene as needed"

#### Todo List Generation

**Automatic Breakdown**: "Cascade generates Todo lists for complex tasks with automatic updates based on discovered information"

**Dynamic Adaptation**: Tasks update as agent discovers new information during execution

#### Queuing System

**Sequential Execution**: "Queuing system allows users to stack messages for sequential execution while the agent works"

**Parallel Sessions**: Multiple independent queues when using worktrees (no cross-queue communication)

## 2. Memory & Context Management

### Per-Agent Context

#### Context Window
- **Size**: "32K-64K tokens" of full codebase context
- **Comparison**: Comparable to Cursor and GitHub Copilot
- **Limitation**: User reports indicate "context window indicator" added in Wave 13 for visual feedback, suggesting previous context overflow issues

#### Memory System Architecture

**Storage Location**: `~/.codeium/windsurf/memories/`

**Three-Layer Structure** (mimics human cognition):
1. **Working Memory**: Immediate task context
2. **Short-Term Memory**: Session-level information
3. **Long-Term Memory**: Persistent project knowledge

**Content Types**:
- User stories
- Architectural decisions
- Process changes
- Technical standards
- Troubleshooting steps

**Persistence Mechanism**:
- **Memories**: Automatically generated by Cascade AI system
- **Rules**: Manually defined by users

#### Conversation History Management

**Limit**: 20 conversations maximum
- 21st conversation causes first conversation to be deleted permanently
- **User Complaint** (GitHub Issue #136): "Remove or increase limit of past conversations in Cascade (Windsurf)"

**Retrieval via @-Mention**:
> "When referencing previous conversations via @-mention, Cascade retrieves the most relevant and useful information like conversation summaries and checkpoints, and specific parts of the conversation that you query for, but typically will not retrieve the full conversation as to not overwhelm the context window"

**Intelligent Filtering**: System summarizes rather than loading full conversation history

#### Checkpoints System

**Purpose**: "Named snapshots of the current state of your project from within the conversation, which you can easily navigate to and revert at any time"

**Storage**:
- `Checkpoints` folder with timestamps in filenames
- Documents changes between checkpoints
- Version history for rollback capability

**Warning from Docs**: Revert operations include "warnings about irreversibility"

#### Worktree Context Isolation

**Per-Worktree Separation**:
- Each worktree contains repository copy
- Excludes `.env` files by default
- Excludes non-version-controlled packages
- Separate file system prevents accidental cross-contamination

**Context Sharing Challenge**: No documented mechanism for agents to share discovered information across worktrees

### Shared Repository Knowledge

#### Graph-Based Reasoning System

**Architecture** (from marketing materials):
> "Cascade utilizes a graph-based reasoning system to map out the entire codebase's logic and dependencies, allowing Windsurf to maintain 'Flow'—a state of persistent context where the AI understands not just the current file, but the architectural intent of the entire project"

**Proprietary Models**:
> "Proprietary models built to ingest this shared timeline"

**Technical Specifications**: NOT DISCLOSED (no details on graph construction, updating, or querying)

#### MCP (Model Context Protocol) for Shared Resources

**Architecture**: "Windsurf acts as an MCP host, and its integrated AI assistant, Cascade, functions as the MCP client"

**Configuration**: `~/.codeium/windsurf/mcp_config.json` - "Contains a list of servers that Cascade can connect to"

**Shared Tool Access**:
- GitHub repository data (via `github-mcp-server`)
- Database connections (via `deephaven-mcp`)
- AWS CodePipeline (via `mcp-codepipeline-server`)
- Custom FastAPI endpoints

**Benefit**: "MCP is an open standard that enables AI agents like Cascade to seamlessly connect with external tools, data sources, and services"

**Limitation**: MCP provides shared tools, NOT shared memory between parallel agents

#### Enterprise Rules & Workflows

**System-Level Configuration** (Wave 13 feature):
> "Enterprises can deploy configurations via MDM policies. Organizations can place rules and workflows files on users' machines"

**Scope**: Global `.codeiumignore` configuration for cross-repository ignore rules

**Purpose**: Consistent behavior across all Cascade instances in organization

## 3. Task Distribution & Scheduling

### Manual Distribution Model

**No Automatic Task Scheduler**: Windsurf does NOT automatically distribute tasks to parallel agents

**Developer-Driven Workflow**:
1. Developer manually spawns Cascade session in worktree mode
2. Developer assigns specific task/bug to that session
3. Agent works independently
4. Developer monitors via multi-pane interface
5. Developer manually merges results

**Example** (from byteiota):
> "Five separate Cascade agents running simultaneously on different bugs"

**Real-World Practice** (incident.io):
> "They've gone from no Claude Code to simultaneously running four or five Claude agents, each working on different features in parallel"

**Implication**: Human is the orchestrator, NOT an autonomous swarm coordinator

### Arena Mode: Competitive Parallelism

**Purpose**: NOT task distribution, but **model comparison**

**Workflow**:
1. Click arena button in model picker
2. Choose Battle Group (Frontier or Fast)
3. **Same prompt** sent to multiple models
4. Each model gets isolated worktree
5. User manually evaluates outputs
6. Click "X is better" to converge

**Key Difference from Swarm**: All agents receive identical task, NOT different subtasks

### Planning Mode: Hierarchical Task Breakdown

**Two-Tier Task System**:

**Tier 1 - Planning Agent**:
- Receives high-level goal
- Generates `plan.md` with task breakdown
- "Continuously refines the long-term plan"
- Uses more powerful model

**Tier 2 - Execution Agent**:
- Reads tasks from `plan.md`
- Executes specific coding actions
- Uses user-selected model
- Reports completion back to plan

**Sequential Execution**: Tasks executed one-by-one by single agent, NOT distributed to parallel agents

**Developer Intervention**: "Enabling developers to intervene as needed"

### Queuing System

**Single-Agent Queue**: "Allows users to stack messages for sequential execution while the agent works"

**Multi-Agent Queues**: Each worktree session has independent queue

**No Cross-Queue Coordination**: Agents do not share queue state or task status

### Limitations (NOT ADDRESSED)

**Missing Features**:
- No automatic load balancing between parallel agents
- No task dependency graph for coordinating related tasks
- No priority system for task scheduling
- No deadlock detection when agents need same resources
- No automated task splitting based on agent capabilities
- No work-stealing when one agent finishes early

## 5. Mailbox / Inbox Implementation

### Finding: NO INTER-AGENT COMMUNICATION

**Search Results**: Exhaustive search for "windsurf cascade inter-agent communication mailbox" returned **ZERO relevant technical documentation**

**Evidence**:

1. **Worktree Isolation by Design**:
   > "Each Cascade conversation operates in its own isolated session"

2. **Arena Mode Independence**:
   > "Users can work independently in each conversation—accepting or rejecting changes and asking follow-up questions—without affecting other sessions"

3. **Manual Convergence**:
   > "When ready to commit to an approach, clicking an 'X is better' button discards other conversations"

4. **No Coordination Mechanisms**: Documentation describes agents as parallel workers, NOT coordinating swarm

### What Windsurf DOES Have (Not Agent-to-Agent)

#### Developer-to-Agent Communication

**Input Channels**:
- Text prompts in Cascade interface
- Voice input (mentioned in docs)
- @-mentions for referencing conversations, files, checkpoints
- Clipboard monitoring
- File edit monitoring
- Terminal command monitoring

**Output Channels**:
- Cascade conversation pane
- File edits
- Terminal commands executed
- Todo list updates
- Plan.md updates

#### Agent-to-Developer Communication

**Mechanisms**:
- Conversation responses
- Code diffs
- Terminal output
- Checkpoints (state snapshots)
- Memories (stored knowledge)
- Todo lists (task tracking)
- Plan.md (strategy document)

**Context Window Indicator** (Wave 13):
> "Visual feedback showing current context utilization to help anticipate limits"

#### Shared Resources (Not Message Passing)

**MCP Servers**: Enable shared tool access, NOT agent communication

**Example**:
- Agent A queries GitHub via `github-mcp-server`
- Agent B queries same GitHub server
- **BUT**: Agent A cannot send message to Agent B via MCP
- **MCP provides**: Shared external data sources
- **MCP does NOT provide**: Inter-agent messaging protocol

**Git Repository**: Shared via worktrees, but:
- Each agent on different branch
- No real-time synchronization
- Merge happens manually after agent completes
- No conflict resolution coordination between agents

#### Enterprise Rules & Workflows

**Global Configuration** (MDM deployment):
- Rules files deployed to all user machines
- **Purpose**: Consistent behavior across agents
- **NOT**: Message passing or coordination

**`.codeiumignore`**: Shared ignore rules
- **Purpose**: Consistent file filtering
- **NOT**: Communication channel

### Comparison to True Swarm Architectures

**What Windsurf Lacks** (compared to e.g., AutoGen, CrewAI):

1. **Message Bus**: No pub/sub or queue for agent messages
2. **Shared Memory**: No distributed state store (agents have isolated memories)
3. **Coordination Protocol**: No handshakes, acknowledgments, or coordination primitives
4. **Task Delegation**: No agent-to-agent task assignment
5. **Result Aggregation**: No automatic result combining from parallel agents
6. **Consensus Mechanisms**: No voting or agreement protocols
7. **Agent Discovery**: No registry for agents to find each other
8. **Roles**: No specialized agent roles (all Cascade agents identical)

**What Windsurf Has Instead**:
- **Parallel Isolation**: Multiple agents work independently
- **Human Orchestration**: Developer coordinates via git merge
- **Shared Tools**: MCP servers for external resources
- **Shared Code**: Git repository (post-merge)

### Architectural Classification

**Windsurf Wave 13** = **Parallel Independent Agents**, NOT **Swarm/Multi-Agent System**

**Key Distinction**:
- **Swarm**: Agents communicate and coordinate autonomously
- **Windsurf**: Agents work in isolation; human merges results manually

**Closest Analogy**: Parallel CI/CD jobs (independent, no communication, results aggregated externally)

## Summary: Technical Architecture & Open Source Landscape

### Prompting & Models
Windsurf supports frontier models (GPT-5.2, Claude Opus/Sonnet, Gemini 3 Pro) and fast models (SWE-1.5, Haiku, Gemini Flash). **Dual-model planning system**: powerful model for long-term strategy, user model for execution. Arena Mode enables blinded comparison via Battle Groups. **No official prompt engineering guide**. Community fills gap with `awesome-windsurf`, `windsurf-antigravity-rules`, `cascade-memory-bank`.

### Memory & Context
**32-64K token context**. Three-layer memory (working/short-term/long-term) stored in `~/.codeium/windsurf/memories/`. Checkpoints enable state snapshots. **20-conversation limit** (21st deletes first). Worktrees provide isolated file systems per agent. MCP servers enable shared external resources (GitHub, databases, AWS). **No shared memory between parallel agents**.

### Task Distribution
**Manual distribution only**. Developer spawns sessions, assigns tasks, monitors via multi-pane UI, manually merges. Planning Mode breaks tasks hierarchically (plan.md) but executes sequentially. Arena Mode duplicates tasks for comparison, NOT distribution. **No automatic scheduler, load balancer, or task coordinator**.

### Validation & Quality
Arena Mode: user-driven manual comparison (no automated metrics). Auto-linting fixes syntax errors. Cascade Hooks enable custom validation via shell scripts (SOC 2 audit logging, policy enforcement). **DORA 2025: 91% PR review time increase** exposes human bottleneck. User reports: crashes, inconsistency, rate-limiting. **No automated code review, security scanning, or cross-agent consistency checks**.

### Inter-Agent Communication
**NONE**. Exhaustive search confirms: agents work in **isolated worktrees** with **no message passing**. Manual merge via git. MCP provides shared tools, NOT agent communication. Windsurf = **parallel independent agents**, NOT swarm/multi-agent system. Human orchestrates; agents do not coordinate autonomously.

### Open Source Artifacts (EXHAUSTIVE)

**Community Projects**:
1. `windsurfinabox` - Docker headless Cascade (Apache-2.0)
2. `windsurf-demo` - Official demo app (Python/JS)
3. `windsurf-antigravity-rules` - Prompt templates
4. `cascade-memory-bank` - Memory system helpers
5. `awesome-windsurf` - Resource hub
6. `ccpm` - Claude Code project manager (parallel agents)
7. `WindsurfVisualStudio` - VS extension
8. `windsurf-context-engineering` - Context optimization

**MCP Servers**:
- `github-mcp-server` (official Docker)
- `deephaven-mcp` (database)
- `mcp-codepipeline-server` (AWS)
- Community tools: LM Studio, FastAPI, Stagewise, Biome

**Open Standards Used**: MCP protocol, Git worktrees

**Closed Source** (NOT available):
- Windsurf IDE core
- Cascade agent implementation
- SWE-1.5 model (weights, architecture, base model name)
- Planning agent
- Arena Mode datasets/results
- Worktree orchestration layer
- Hooks execution engine
- Proprietary graph-based reasoning
- Inference infrastructure (Cerebras partnership)

**Academic**: SWE-Bench Pro benchmark open source; SWE-1.5 model NOT released.

**Key Gap**: NO open-source agent coordination framework. Community must build custom solutions (e.g., `ccpm`) for true multi-agent orchestration.
